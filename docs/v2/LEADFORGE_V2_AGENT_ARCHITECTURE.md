# LeadForge V2 agent architecture

Proposed logical roles, not deployed agents. Baseline 2026-10-12, `641658e`. Current executable Lead Brain is the bounded company/contact/intent/qualification graph; names below describe future domain capabilities, not a reason to resurrect legacy agent generations.

## Agent contract and execution boundary

Every AgentRun receives a tenant-bound task, principal/capability grant, immutable goal/Brain/policy versions, allowed subject IDs, evidence references, conversation snapshot, budget/time limits and registered tool allowlist. It returns a validated typed result: assessment, proposal, observation or explicit insufficient-evidence outcome. It never receives raw OAuth/session secrets or database credentials.

The Tool Gateway validates schema, tenant/resource membership, permitted tool/version, actor grant, current run state, budget, stop epoch and policy. Any state-changing effect becomes an ActionIntent and uses the dispatcher. Tools cannot accept arbitrary SQL, shell commands or model-selected URLs; research URLs require licensed source policy, egress allowlist and SSRF controls. Delegation can only reduce parent authority/budget/deadline and cannot grant a child tool absent from the parent.

Shared run state: created → running → waiting_tool / waiting_approval → completed / failed / cancelled / reconciliation_required. Outputs persist with schema/prompt/model/tool versions and provenance. Reasoning summaries are user-facing rationale with evidence, not hidden chain-of-thought. Persistent customer memory comes from governed Brain/timeline facts, not a model's private uncontrolled memory.

## Guarded memory and tool results

Business Brain and relationship timeline are shared by permission, not separate channel/model memories. Run checkpoints reference revisions and do not silently refresh input semantics after approval. A new fact can invalidate a proposal and trigger replan; it cannot mutate an approved payload in place.

Tool results carry provenance and data classification. External pages, CRM notes, email bodies and transcripts cannot instruct the gateway to broaden permissions. Tool output schemas reject nested commands, secret-return fields and unbounded content. Retrieval applies organization filters before rank/limit and permission checks before prompt assembly; artifact references are fetched only after authorization.

Agent-to-agent messages are typed task/results linked by parent_run_id and causation_id. Parallel agents may propose competing facts but do not concurrently overwrite confirmed facts; optimistic revision checks create conflict review. A single action owner/fenced dispatcher prevents two agents from issuing the same touch.

## Execution limits and evaluation

Per-run caps include model calls, tool calls, elapsed time, data volume and estimated spend. Delegation and retries consume the same shared reservation, not fresh budgets. Exceeding limits emits a safe failure/approval request; no recursive self-extension. Provider switching requires explicitly approved data-processing/quality equivalence.

Required mock-provider suites: tenant isolation for every tool; invalid structured output; hallucinated evidence; prompt injection; revoked grant mid-run; duplicate tool calls; provider timeout; exhausted budget; approval replay/expiry; cancellation; ambiguous send; transcript consent mismatch; user-confirmed fact contradiction. Behavioral evals measure evidence support, safe abstention, false-positive qualification, harmful commitments, reply escalation and cost, using tenant-safe synthetic fixtures.

Promote agents through read-only shadow → human-reviewed proposals → restricted sandbox actions → approved limited production cohort. A successful model demo is not a release gate. Agent definitions, evaluations and tool versions must be reviewable independently; new external-effect capability is a security change.
