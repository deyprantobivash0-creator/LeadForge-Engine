## Decisions: minimum write-side scope

An **AuditEvent** is a bounded server-authored record of a committed protected command or an attributable structural rejection, with tenant, actor/provenance, action, authority evidence, target and result. It is neither a command, an authorization grant, a queue message nor a full customer-record snapshot. A pending append is not a durable event until its owning transaction commits.

Initial integrations are exactly `LeadService.create_lead`, `LeadLifecycleService.update_lifecycle`, `LeadImportService.confirm`. Machine create/lifecycle uses the same API and evidence model as human execution; no separate machine audit route. Import remains browser USER/session-bound.

| Proposed event_type | Outcome | Initial meaning |
|---|---|---|
| `business.command.completed` | SUCCEEDED | Successful canonical command result committed with required audit row. `action` disambiguates create/lifecycle/import. |
| `permission.denied` | DENIED | First decisive structural permission rejection captured by an application/audit boundary; persistence is best-effort after settlement. |
| `security.command.rejected` | DENIED | Explicit tenant mismatch attributable to an already trusted, valid principal; no permission result is invented if evaluation did not occur. |

`action` uses the three enforced E04 action strings; event_type describes what happened, not authority. Outcomes initially enumerate **SUCCEEDED, DENIED**. FAILED is deliberately not accepted in v1; business validation, conflict, not-found and infrastructure failure remain operational diagnostics. Later FAILED/CANCELLED/EXPIRED/UNKNOWN, workflow/policy/approval/provider events require reviewed typed schemas and transaction semantics before enum/CHECK extensions. No free-form outcome/event type.

Missing/invalid principal, malformed tenant selector, authentication/CSRF/membership rejection before a trusted principal exists: operational security evidence only. Do not fabricate a tenant, trust a submitted organization, or add nullable organization to this business table. A command's explicit target-tenant mismatch is recorded under the valid principal's organization, with target ID omitted and no other-tenant identifier in details. Unknown/nonexistent scope cannot safely produce a tenant ledger record. These exclusions are coverage boundaries, not successful auditing claims.

Login success/failure, password change and session revocation are **deferred account-security follow-up**. User is global and login precedes workspace selection; copying an account event to every membership would leak or duplicate evidence. Design a separate account/platform security stream before integrating auth; retain current protections/logs. Public audit API/UI, `audit.read`, processing/read adoption, provider effects, usage, grants and workflow tables are deferred. Do not change E04 grants to expose sensitive audit data incidentally.

## Successful command transaction

Within the existing E02 owning scope: validate trusted principal/tenant -> resolve fresh E04 decisions -> mutate through private helper/repository -> form safe audit draft from server results -> append/flush using **the same injected Session** -> outermost COMMIT. An inner command may return before root commit; its audit row is provisional until then. Every successfully committed canonical invocation appends exactly one command event, including nested commands that eventually commit.

No repository/service dedicated to audit commits this success row independently. No after-commit success writer, logger-to-audit conversion, background best-effort success append or separate engine transaction. Audit validation/flush/constraint/DB failure escapes the command, marks root rollback-only, and prevents business commit. An outer later failure removes both earlier mutations and their audit success rows. A commit transport failure is ambiguous: the pair may have committed together; rollback cannot prove absence. Do not claim exactly-once HTTP acknowledgment or automatically retry a business command. E07/E09 will address durable delivery/semantic command identity.

### Command-specific evidence

* **Create:** capture PERMIT -> `_create_lead_internal` allocates Lead ID -> event targets `lead`/decimal ID, no company/email/source -> append -> root commit. Duplicate/precheck/NOT NULL/commit failures never append a surviving SUCCEEDED event.
* **Lifecycle:** PERMIT -> tenant-scoped locked load and scalar status-before inside owning scope -> `_apply_lifecycle_change` -> capture persisted status-after and allowlisted changed field names -> append -> root commit. A future repository integration must acquire PostgreSQL row ownership with SELECT FOR UPDATE before capturing the before value, so competing writers cannot make it a stale transition snapshot. SQLite uses a real write transaction before the read (BEGIN IMMEDIATE when appropriate); lock conflicts must fail/roll back safely, never claim a stale before value. This locking integration does not exist today and needs explicit concurrency tests. No owned Lead gives existing not-found and no success event. A valid no-op update may still produce one SUCCEEDED command event with `changed_fields=[]`; success means accepted command, not necessarily changed values. Preserve input validation. Never capture notes, dates or whole ORM objects as details.
* **Import:** collect BOTH individual decisions -> `_confirm` verifies existing preview token/digest/user/session and re-evaluates rows -> savepoint batch -> one event with total/imported/duplicates/invalid counts -> root commit. Includes valid all-duplicate/no-op confirmation. Target `lead_import` uses the server-generated event UUID as an opaque operation reference. No token, session signing material, CSV contents, filename, digest or list of up to 1,000 Lead IDs. One command event, not one per Lead: avoid amplification. Per-row lineage/import history is a separately reviewed future domain feature; this ledger alone cannot enumerate every imported Lead.

For audit failure after released row savepoints, the real outer SQLite transaction must roll back the entire batch. E04 authoritative decision objects must be retained by the command for audit; recomputing them afterwards or querying a new role would misrepresent the authority actually evaluated.

## Guarantees and best-effort denial recording

**MUST HOLD:** a successful consequential command cannot commit without its required audit event in the same transaction. **MUST HOLD:** audit failure cannot convert DENY to PERMIT. **MUST HOLD:** a denied command performs no business mutation. **BEST-EFFORT:** durable denial evidence after the owning business transaction settles; process/database failure may prevent persistence. Failed business command durable audit, cryptographic tamper evidence and account/global security events are deferred.

Choose a short independent rejection-audit transaction AFTER root settlement. Never insert denial evidence into the rolled-back business transaction or commit that Session as audit-only: earlier nested writes could then commit. Never start an independent SQLite write while the owning transaction is still active.

### E02 coupling decision: no transaction-helper extension

Re-inspected backend/services and registered route callers. The three protected canonical commands use E02 scopes and private helpers; no production use case currently composes those protected commands under a wider owning service transaction. Authentication nesting and processing phases are separate excluded paths. Concrete nested protected-command examples exist in tests: test_denied_nested_command_cannot_commit_early_write (create -> denied lifecycle), test_principal_domain_tenant_mismatch_rolls_back_outer_command, and E02 test_caught_inner_failure_marks_outer_rollback_only. They prove nesting requirements, but do not justify introducing audit knowledge into E02. Its failed-state marker, root rollback and TransactionAborted behavior remain unchanged; do not add audit drafts, permission enums, callbacks, persistence dispatch or a new abort-on-entry rule to backend/database/transactions.py.

Propose an **application/audit-service operation boundary**, with explicit caller-owned audit context when composing commands. It contains no authorization fallback or unchecked mutation API:

1. For today's standalone commands, the canonical service invocation establishes its audit operation boundary OUTSIDE its own E02 scope. Permission checks and mutation remain inside that scope. After scope exit, the boundary knows whether root settlement finished; success evidence was already appended atomically inside it.
2. At the narrow rejection check site, build a typed immutable rejection draft from known trusted principal and actual decision evidence. The audit operation context retains the first decisive rejection; it is explicitly supplied between composing services, not a global/ContextVar or E02 Session.info authority source. It never supplies permissions.
3. A future composing application use case establishes that boundary around the outermost `with service_transaction(db)` and passes its context explicitly to canonical commands. Inner services capture drafts but cannot persist them yet. The outer boundary catches the original rejection or TransactionAborted only AFTER E02 root exit, then invokes the rejection recorder. Catching an inner denial never commits earlier writes: existing E02 rollback-only semantics govern that result. Do not change E02's current handling of subsequent nested calls.
4. The application/audit boundary attempts persistence once after confirmed rollback/connection release, using an explicitly injected independent Session factory for the SAME configured database. AuditRepository only appends/flushes; the audit service owns this separate audit-only transaction and close. It never re-evaluates permission in a way that erases the captured denial and never reuses the active business connection. No recursive recording of audit-recorder failures.
5. Preserve the original safe rejection, or the existing TransactionAborted behavior for a caught nested rejection. Audit failure emits `audit.rejection.persistence_failed` with bounded safe IDs/enum reason, without SQL/connection/error payloads. Authorization remains DENY and the denied command makes no mutation. After successful normal rollback a fresh command may use the cleaned caller Session; failed rollback/invalidation requires discarding it.

An arbitrary caller may already own an E02 scope but supply **no application audit context**. The inner service cannot know when that owner will settle. In that case keep authorization and rollback behavior intact, emit safe `audit.rejection.recording_deferred_unavailable` coverage-loss diagnostics, and do not open a second writer or guess settlement. No durable denial row is promised for that unsupported audit composition. Future production compositions must use the explicit boundary to obtain best-effort recording. Successful nested commands still append required success evidence inside the existing transaction regardless of this rejection context. Tests must cover both contextual composition and legacy external-scope fallback; a route-only handler does not cover standalone service calls.

At most one first-decisive rejection draft per explicit audit operation; not every evaluator invocation or every subsequent blocked attempt. No global queue, audit-aware E02 hook, new UoW, outbox or worker. If a future production call graph makes explicit boundary composition materially impossible, a generic transaction settlement primitive may be proposed separately with concrete caller evidence and generic lifecycle tests. None is retained in D2.

### Exact persistence acceptance language

"Successful consequential command auditing is transactionally mandatory. Structural denial auditing is best-effort durable after business transaction settlement. With a valid captured rejection, confirmed settlement, configured boundary and available audit storage, the recorder attempts one bounded append/commit. There is no guarantee that every denial is losslessly recorded across process/database failure. Audit persistence failure never changes DENY, never causes the denied command to mutate business state, and produces safe operational evidence-loss diagnostics when the process can emit them."

Proposed maximum recorder deadline: 5 seconds total including pool acquisition/connect/statement/lock work; individual 5-second timeouts are not a total-budget proof. Test driver/call-path enforcement during implementation; skip unsafe persistence when cleanup cannot be confirmed. No recursive or automatic retry, no infrastructure details in client error. Process death after denial establishment (including before rollback), after settlement or before rejection commit, storage outage/exhaustion, missing outer audit context, and ambiguous audit commit can all leave absent/uncertain evidence. Hard process death may also prevent diagnostics. Do not label these cases mandatory denial durability or silently report a PASS count as zero-loss evidence.

Lossless intake is not an initial E05 guarantee. If architecture/product later requires it, a separately durable intake/spool design is needed; an outbox in the rolled-back transaction cannot solve that gap.

## Bounded repeating authorization evidence

Replace fixed permission/additional_permission slots with **authorization_evidence JSON**: a required closed-schema list of 0..8 objects, each with EXACTLY permission, decision, reason_code. Values are serialized E04 ActionPermission, PermissionResult and PermissionReason enum values. Evidence is constructed from actual server evaluation receipts, never accepted as caller/client JSON, never used to grant authority, and never reconstructed from log/exception text. No duplicate permission entries in v1; preserve actual evaluation order (import: lead.import then lead.create), with fixed object-key serialization, compact separators and UTF-8. Cap the entire canonical evidence value at **2,048 bytes**, independently of details' 2,048-byte cap.

One evaluated permission -> one item. Successful import -> exactly two PERMIT items for lead.import and lead.create. A first-check import denial -> one actual DENY item (second requirement is known from action, not a fictional unevaluated result); second-check denial -> first PERMIT plus second DENY. Attributable tenant rejection before evaluation -> empty list. Initial action-specific validators reject missing, extra, duplicated or out-of-order checks; the generic eight-item container bound does not authorize new actions or let create accept eight checks. A later reviewed multi-check command may reuse this representation without adding numbered columns.

The list has one repeated schema, a tiny bounded cardinality and no independent lifecycle/joins, making portable JSON appropriate. Important tenant/actor/action/outcome/target/correlation query dimensions stay explicit columns; there is no evidence JSON query index or child table. Revisit normalization only after measured evidence-query/volume requirements, not speculative extensibility.

**authority_version is removed.** Current E04 has no authoritative policy/grant version source. Do not invent e04-1, use an application build SHA as authority, or repurpose schema_version. Keep actual reason/decision and an optional human role captured from the same server-side evaluation. Future genuinely versioned grants/policies can introduce meaningful references through their own reviewed extension.

## Historical organization identity decision

Choose a **non-null historical organization_id with no hard FK**, matching current integer tenant IDs. All tenant-leading read predicates remain required; the identifier is server-derived from trusted validated scope, never a raw selector. Ordinary success builders verify current tenant/resource ownership and organization existence before append; denial uses the trusted tenant captured at rejection time and may persist after organization deletion without a live join. Unknown/unvalidated scope is not made legitimate merely because no FK rejects it.

A hard FK+RESTRICT offers referential integrity but turns audit retention into a gate on future physical organization deletion, couples evidence cleanup to SaaS lifecycle and requires extraordinary deletion sequencing. Removing that FK preserves historical identity and append-only rows while leaving privacy/deletion policy to a separately authorized lifecycle service. It trades DB orphan prevention for strict server writer validation, scoped reads and explicit historical interpretation. A ledger row whose former organization no longer exists is intentionally valid evidence, not permission to access a live tenant.

No cascade, SET NULL or rewrite on organization deletion. Physical deletion does not itself erase ledger evidence and does not establish privacy compliance; exceptional retention/hold/erasure remains separately governed. Tenant IDs must never be reassigned to a different workspace: SQLite's allocator alone cannot ensure this. No customer organization-delete/create API is introduced by E05. Before implementing physical deletion/re-provisioning, require permanent non-reuse or a separately designed immutable tenant-generation mapping and tenant-isolation tests. Without that identity lifecycle guarantee, that future deletion feature is blocked; do not join historical events to a newly recycled organization ID.

## Append API, reads and hardening

Proposed `AuditRepository.append(validated_draft)` adds and flushes only, returns an immutable receipt, not a mutable ORM entity. It requires a caller-owned service scope. An AuditService builder validates server-derived event schema, authority/tenant binding and bounded details. No generic CRUD/save/update/delete API. Use Core INSERT or guarded ORM append; prohibit ORM UPDATE/DELETE on AuditEvent with before_flush guards and tests. These guards do not intercept arbitrary Core/raw SQL.

Internal query APIs require explicit tenant: `get_event(organization_id, event_id)` and bounded keyset `list_events(organization_id, filters, cursor, limit)`. Never an unscoped event lookup or operator flag. Read DTOs omit arbitrary payload exposure. No public query service/route is introduced; future customer reads require live membership plus separately reviewed audit.read mapping, with cross-tenant denial tests. Opaque IDs are not authorization.

**Recommended v1 guarantee:** append-only application contract, restrictive writer API, validated constraints and transactional durability. Not immutable and not cryptographically tamper-evident. Existing app role broadly receives DML; naming it restricted does not make audit rows protected against that role. Keep deployment privilege changes out of the additive portable E05 migration and out of this task.

**Next deployment hardening gate:** explicitly grant SELECT/INSERT only on audit_events to the app role; revoke table UPDATE/DELETE/TRUNCATE, ensure it is not owner/migrator/superuser and cannot assume those roles, and preserve backup read/operator migration permissions. Broad/default grant provisioning can regrant access: audit-table carve-out and re-provision regression are required before claiming resistance to app-role history modification. Do not claim resistance to INSERT fabrication by a compromised writer. No trigger initially: dialect divergence, controlled retention, restore and migration exemptions need reviewed operational procedures; privileges are simpler when actual topology is verified. SQLite remains application-contract testing, not role-isolation proof. Do not execute grants or inspect live Render here.

Cryptographic tamper evidence: **LATER**, not needed for initial atomic write evidence. Per-tenant previous-hash chains can serialize inserts or fork under concurrency; administrators can rewrite both rows and hashes without a protected external anchor. Later independent signed checkpoints/protected archives, canonical serialization, key custody and restore/retention reconciliation need their own design. Ordinary backups/checksums do not prove an untampered ledger or prevent deletion of a tail.

## Privacy, details and retention

Use pseudonymous stable IDs; they can still be personal data and require controlled access. No names, email addresses, phone numbers, lead/customer bodies, IP/user agent, message bodies, prompts, model reasoning, provider response, transport headers, tokens, password/hash, API keys or DB credentials in v1. Do not persist hashes of email/CSV as a supposed privacy fix: they can be linkable. No full before/after snapshots. Public schema validation refuses unknown fields; trusted builders construct exact dictionaries, never `model_dump()`/`vars()` of a customer/session/request object. Runtime redaction is defense in depth, not permission to store a secret and scrub it later.

Details are constructed ONLY by event-specific server allowlists, not arbitrary caller-provided dictionaries. Prohibit serializing ORM models/request bodies, and prohibit "sanitize then store everything". Details are JSON objects, <=2,048 UTF-8 bytes in canonical serialization, depth <=2, no floats/NaN, at most 8 keys. Closed per-event schemas: create `{}`; lifecycle status_before/status_after from existing vocabulary plus changed_fields enum list (status/notes/last_contacted/next_follow_up, no values); import integer total/imported/duplicates/invalid (0..1000, arithmetic validated); rejection `{}`. Reject excess/unknown/secret-like keys and invalid values rather than silently trimming required evidence. Schema validation failure aborts successful business command. Denial draft validation failure preserves denial and signals evidence loss. JSON must never determine authority or query tenant scope.

Retention assumption: bounded minimal collection in the first **non-production implementation**, no automated expiry/purge job; no promise of forever retention. Before deployment/real customer collection, a named privacy/security owner must approve retention duration, legal-hold handling, access/export/deletion procedures, backup expiry and restored-deletion replay. No universal duration or compliance certification is asserted. Organization/actor/target snapshots survive deletion without a hard FK or cascade; future tenant ID reuse must be prevented. Future controlled tenant erasure must coordinate ledger, backups and holds; application append-only permits an exceptional independently authorized retention/privacy operation, not a user-facing delete method.

An appended redaction marker can explain authorized removal/supersession but **does not erase old PII**. If future sensitive payloads become essential, store them separately with governed encryption/expiry and references; erasure/archives/partitions need separate authorization. No plaintext-sensitive schema is introduced now.

## Threat model and future relationships

| Threat | v1 protection / remaining limit |
|---|---|
| Malicious tenant or forged actor/metadata | Existing auth/CSRF/E03/E04 and server builders; no audit payload endpoint. Tenant selector/request ID grants nothing. |
| Compromised endpoint / application bug | Canonical command atomic success append, typed writer and guarded ORM writes. Arbitrary backend code/raw SQL can bypass application conventions; no sandbox claim. |
| Compromised agent / prompt injection | No new agent/tool ingress or model-authorized write; same canonical permission boundary. Valid compromised scope can still perform allowed commands; ledger records rather than prevents them. |
| Tenant crossover | Required historical tenant ID, scoped reads, validated tenant/target writers and non-reuse lifecycle gate, no client target snapshot before ownership verification. Audit table has no RLS yet; compromised DB access is broader. |
| DB app-role compromise | Initial broad DML can alter/delete/fabricate records; later privileges reduce alteration, not authorized-writer fabrication. |
| DB owner/admin compromise | Can alter schema/data/backups; outside v1 guarantee. External independent anchoring needed to detect historical rewrite. |
| Log injection | No exception text/customer fields; typed reasons and bounded correlation/IDs. Correlation is untrusted grouping, never causal proof. |
| Storage amplification / denied-event abuse | One first denial per root, bounded draft/details and indexed minimal rows; no per-import-row audit. Repeated distinct denied operations still amplify storage; existing rate limits are insufficient for shared budgets. |
| Persistence outage / process crash | Success fails closed; rejection remains denied with explicit evidence-gap diagnostics. No durable buffer or zero-loss claim. |

Require capacity forecasts and denial rate/error monitoring before release. Do not silently sample/drop successes; disk exhaustion must block their commit. Any future denial sampling must disclose coverage and aggregation semantics. Distributed abuse controls are deferred, not claimed implemented by a per-event byte cap.

E07 outbox/inbox delivers/deduplicates messages; audit is historical evidence, not transport. Both may share a later transaction, but neither substitutes for the other. E09 ActionIntent is an immutable proposal/execution contract, not an audit event; it can reference event_id and correlation without E05 creating its table. E10/E11 add typed policy/approval events and version references in reviewed schema extensions; no policy/approval decision is inferred from E04 PERMIT. Revenue Decision Ledger may link evidence and actual effects to these minimal records; E05 is not a complete causal revenue ledger.

## Decided, open and deferred

**Proposed decisions for architecture approval:** three commands; atomic success; application-boundary first decisive rejection best-effort after settlement; E02 unchanged; bounded evidence gaps on crash/outage; tenant-required one table; historical organization/actor/target snapshots with no hard FKs; UUID4; two UTC timestamps; bounded repeating authorization evidence for import AND; no synthetic authority version; no public reads; application append-only initially; no cryptographic chaining.

**Open approvals:** final 22-column schema and explicit application-boundary integration; testable 5-second recorder budget; before production, privacy retention/deletion/hold owner and audited role carve-out/capacity plan. Best-effort denial is the selected guarantee, not an unresolved promise of lossless auditing. Any future demand for lossless intake or physical tenant deletion with recyclable IDs requires a separately approved design. This task authorizes no implementation.

**Deferred:** account/platform stream, failed-command persistence, public audit API/UI/audit.read, read/process events, persistent grants, explicit multi-hop causation records, per-row import lineage, tamper checkpoints/archive, automated retention/redaction, E06+ infrastructure and policy. These require independent scope and migration reviews.
